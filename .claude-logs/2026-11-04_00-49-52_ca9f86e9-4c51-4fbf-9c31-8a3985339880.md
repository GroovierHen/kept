## 4. docs/rules/mobile.md, every rule
1. The phone reads and writes data only through `/api/app/v1/*`, using `api()`. Never Prisma, Supabase `.from()`, or another SDK that holds data (9-11).
2. A new endpoint takes three edits:
   - the contract entry, with Zod schemas for query or body and the response;
   - a handler in `apps/web/src/server/app-api/`, typed `AppRouteHandler&lt;typeof endpoints.x&gt;`;
   - a route file that holds only `export const GET = createAppRoute(...)` (12-18).
3. `createAppRoute` runs the bearer check (401), input parsing (400), the handler, and response parsing before sending (a wrong shape is a reported 500). Errors are `{error:{code,message}}` with a message written for the person. Throw `AppError` for something they caused (19-24).
4. The app parses every response and throws `ApiError` otherwise. A screen shows the error message and a retry, **never an empty state for a failed request** (25-27).
5. A shipped endpoint is a public API. Add fields; don't rename or remove one until no supported build reads it (28-30).
6. One file owns each SDK, enforced by ESLint (32-43):
   - Supabase: `src/lib/supabase.ts`, sign-in only.
   - Sentry: `observability.ts` and `logger.ts`.
   - PostHog: `analytics.ts`, using the web's event names.
   - `process.env`: `env.ts` only, `EXPO_PUBLIC_*` spelled out, public keys only.
   - `console`: the logger only.
7. Shared packages (`contract`, `brand`) stay framework-free: no React, Next.js or React Native. After editing brand tokens, run `pnpm --filter @kept/brand build:css` (45-52).
8. Add a mobile package with `pnpm expo install &lt;name&gt;` inside `apps/mobile`, not `pnpm add`. An SDK upgrade is its own change (`expo install expo@&lt;next&gt; --fix`, then `doctor`) (54-60).
9. An over-the-air update carries JS and assets only. A new native package, config plugin or `app.json` change needs a store build, because `runtimeVersion` uses the fingerprint policy (62-68).

- `apps/mobile/AGENTS.md` says: read the versioned Expo docs (v58), not memory; use Expo Router only; keep non-route code out of `src/app/`; never edit `ios/` or `android/`; prefer Expo modules.

  - Error mapping is `userFacingAuthError` (line 36): `user_already_exists`/`email_exists` → taken (409), `invalid_credentials` → wrong (401), `weak_password` (400), `email_not_confirmed` (403), rate limits → busy (429). Anything else shows `Auth.errors.failed`.
- **App User row:** there is no callback route and no `ensureUser`. The action itself calls `provisionOrSignOut` (`src/server/auth/provision-or-sign-out.ts:5`) around `provisionUser({id, email, timeZone})` (`src/server/auth/provision-user.ts:22`). If saving the row fails, the Supabase session is closed again.
  - `provisionUser` is idempotent. In one transaction it runs `user.createMany(skipDuplicates)`. A new row also gets the Event `signed_up` (key `signed_up`); an existing row only has its email updated, and its time zone is kept.
  - Afterwards it upserts an `AdminMember` if the email domain maps to a staff seat (`seatRoleForEmail`).
- **Writes:** Supabase auth user; Prisma `User`, `Event(signed_up)`, and possibly `AdminMember`.
- **Redirect:** `landingPage` (line 71) sends the user to `/setup` if `readSetupStep` is non-null, otherwise `/today`. It also deletes the start-email cookie.
